## Phase 05 persistence decisions 23 October 2026

Evidence: [PHASE_05](evidence/PHASE_05.md). Engineering choices made while executing Phase 05; no product rule changed.

| ID | State | Decision and reason | Tradeoff or consequence |
| --- | --- | --- | --- |
| D52 | Engineering baseline | One `AppDatabase` per file behind a small `SqlDriver` boundary (`src/data/db/`). A dedicated write connection runs every mutation as `BEGIN EXCLUSIVE … COMMIT` through one JavaScript promise queue (the serialized write path); a second, `query_only` read connection serves read snapshots, so uncommitted writes are never visible. Both enable `foreign_keys`; the writer sets WAL, `synchronous=FULL` and `busy_timeout=5000`. expo-sqlite's `withExclusiveTransactionAsync` is not used: in 58.0.13 it opens a new connection per transaction and begins the transaction before the task, so foreign keys could not be enabled on it. Migrations: ordered immutable list, history in `migrations` (version, name, FNV-1a 64 checksum, applied time); all pending migrations plus `foreign_key_check` run in one exclusive transaction; newer schema, changed history or a foreign database are refused unchanged. Only `expo-sqlite` imports under `src/data/db/` pass lint. | Writes are strictly sequential (fine for one person's ledger). WAL is set before the history check, so an unreadable file may get only its journal-mode flag changed. Schema 1's checksum is pinned by a unit test; editing a shipped migration fails CI. Every later schema change is a new migration with a new app version/runtime (EAS_AND_OTA). |
| D53 | Engineering baseline | Schema 1 uses STRICT tables and lets the database defend the command invariants: CHECKs for target/amount ranges, statuses, theme IDs, date/timestamp shapes, title 1..100 and note 1..500 characters; triggers forbid goal deletion, changing ids/goal links/createdAt, revision steps other than +1, any ledger change on a completed/archived goal and receipt updates.
